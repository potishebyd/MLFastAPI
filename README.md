🤖 **🤖 ML FastAPI**

📋 **fastapi_churn_overall**

**Общая идея проекта**

Вы разрабатываете учебный сервис на Python и FastAPI для решения конкретной задачи машинного обучения. Задача сервиса — предсказывать отток клиентов **churn** на основе их поведения и характеристик.

🎯 **Конкретная задача классификации**

Клиент может уйти из сервиса в следующем месяце или остаться. Целевая переменная churn принимает значение **1** если клиент ушёл, **0** если остался.

💾 Сервис работает на основе табличных данных. Для обучения модели используется искусственно сгенерированный датасет в файле churn_dataset.csv который входит в это домашнее задание.

📊 **Признаки в датасете**

1. 💰 monthly_fee — ежемесячная стоимость тарифа клиента
2. ⏰ usage_hours — количество часов использования сервиса за последний месяц
3. 🎧 support_requests — количество обращений в техподдержку
4. 📅 account_age_months — возраст аккаунта в месяцах
5. ❌ failed_payments — количество неудачных платежей
6. 🌍 region — регион клиента (*europe, asia, america, africa*)
7. 💻 device_type — основной тип устройства (*mobile, desktop, tablet*)
8. 💳 payment_method — способ оплаты (*card, paypal, crypto*)
9. 🔄 autopay_enabled — включено ли автосписание (*0 или 1*)
10. 🎯 churn — целевой признак (*1 клиент ушёл, 0 клиент остался*)

🚀 **К концу второй недели сервис должен уметь**

1. 📥 Загружать тренировочный датасет через API или использовать локальный churn_dataset.csv
2. ⚙️ Проводить предобработку данных и разбиение на train и test
3. 🎓 Обучать модель классификации churn на основе scikit learn
4. 💾 Сохранять и загружать обученную модель
5. 🎯 Принимать новые объекты и выдавать предсказание churn и вероятности
6. 📊 Показывать базовые метрики качества модели
7. 🧪 Иметь базовые тесты и запускаться в Docker

📅 Ниже каждая из двух недель разбита по дням. Каждый день представляет отдельный шаг в построении полноценного ML сервиса.

## День 1 — Базовое приложение FastAPI

Создание окружения и установка зависимостей:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Запуск из папки проекта:

```bash
uvicorn main:app --reload
```

Проверка: откройте http://127.0.0.1:8000/ или выполните:

```bash
curl http://127.0.0.1:8000/
```

Ожидаемый ответ:

```json
{"message": "ml churn service is running"}
```

Интерактивная документация API: http://127.0.0.1:8000/docs.

## День 2 — Pydantic модели для признаков churn

В `schemas.py` описаны две модели:

- `FeatureVectorChurn` — девять обязательных признаков клиента.
- `DatasetRowChurn` — те же признаки и обязательное поле `churn: int` для обучения.

В день 2 временный `POST /predict` возвращал признаки для проверки структуры.
С дня 7 он выдаёт прогноз обученной модели (см. ниже).

После запуска сервера откройте http://127.0.0.1:8000/docs,
раскройте `POST /predict` и нажмите **Try it out**. Вставьте пример:

```json
{
  "monthly_fee": 29.9,
  "usage_hours": 45.5,
  "support_requests": 2,
  "account_age_months": 12,
  "failed_payments": 0,
  "region": "europe",
  "device_type": "mobile",
  "payment_method": "card",
  "autopay_enabled": 1
}
```

Сначала обучите модель через `POST /model/train`, затем нажмите **Execute**:
ожидается код `200` с прогнозом churn и вероятностями классов.
В разделе **Schema** можно проверить поля запроса и ответа.
Если пропустить обязательное поле или передать значение неподходящего типа,
сервис вернёт `422` с описанием ошибки.

## День 3 — Загрузка и просмотр датасета

Датасет расположен в `data/churn_dataset.csv`. Модуль `dataset.py` читает CSV
и преобразует каждую строку в `DatasetRowChurn`, затем сохраняет проверенные
значения в списке словарей. Путь к CSV определяется относительно модуля.
Файл читается при каждом запросе, поэтому изменения в нём сразу видны.

После запуска сервера доступны:

- `GET /dataset/preview` — первые 5 строк в формате JSON.
- `GET /dataset/preview?n=10` — первые 10 строк. Параметр `n` должен быть
  положительным целым числом; если строк меньше, возвращаются все доступные.
- `GET /dataset/info` — число строк (`row_count`), число столбцов (`column_count`),
  названия всех столбцов (`columns`), входные признаки без таргета (`feature_names`)
  и количество клиентов каждого класса (`churn_distribution`).

Примеры проверки:

```bash
curl 'http://127.0.0.1:8000/dataset/preview?n=3'
curl http://127.0.0.1:8000/dataset/info
```

В текущем датасете 2000 строк и 10 столбцов, включая таргет `churn`:
1597 клиентов остались (`0`), 403 ушли (`1`).

Оба эндпоинта также доступны через http://127.0.0.1:8000/docs.
Если файл отсутствует, возвращается `404`. При некорректных данных в CSV
возвращается `422`, при ошибке чтения файла — `500`.

## День 4 — Предобработка и разбиение на train и test

Установите обновлённые зависимости в активированном окружении:

```bash
pip install -r requirements.txt
```

Модуль `preprocessing.py` отделяет девять признаков `X` от таргета `y = churn`.
Числовые признаки: `monthly_fee`, `usage_hours`, `support_requests`,
`account_age_months`, `failed_payments`, `autopay_enabled`.
Категориальные: `region`, `device_type`, `payment_method`.

`prepare_data(rows)` возвращает объект с `X_train`, `X_test`, `y_train`, `y_test`
и обученным обработчиком `preprocessor`. Используется `train_test_split`:
80% для train, 20% для test, `random_state=42`, `stratify=y` для сохранения
долей классов. Оба класса должны присутствовать хотя бы в двух строках каждый;
размер выборок должен позволять стратификацию.

Пустые признаки в CSV допускаются и отображаются в preview как `null`.
Пропуски числовых признаков заполняются медианой train; если числовой столбец
целиком пуст в train — нулём. Категориальные пропуски заменяются на `unknown`.
Обработчик обучается только на train и затем применяется к test, чтобы избежать
утечки данных. Пропущенный или некорректный таргет отклоняется при загрузке.
В результате `prepare_data` категории остаются строками; обучающий Pipeline
из дня 5 отдельно выполняет их кодирование.

Просмотр размеров выборок, количества и долей классов:

```bash
curl http://127.0.0.1:8000/dataset/split-info
```

Эндпоинт также доступен в `/docs`. Неподходящий для разбиения датасет
возвращает `422` с объяснением причины.

## День 5 — Обучение базовой модели

Модуль `training.py` содержит `train_churn_model(rows)`, которая принимает
список тренировочных строк с таргетом и возвращает обученный `Pipeline`:

- числовые признаки: заполнение пропусков медианой и `StandardScaler`;
- категориальные признаки: заполнение `unknown` и `OneHotEncoder`;
- классификатор: `LogisticRegression(max_iter=1000, random_state=42)`.

Неизвестные при обучении категории поддерживаются через `handle_unknown="ignore"`.
Все обработчики обучаются только на тренировочной части.

`train_and_evaluate(rows)` разделяет данные 80/20, обучает Pipeline на train
и рассчитывает accuracy и бинарный F1 для класса `churn=1` на test.

Запуск обучения через API (тело запроса не требуется):

```bash
curl -X POST http://127.0.0.1:8000/model/train
```

Ответ на текущем датасете:

```json
{"accuracy": 0.7875, "f1": 0.0449438202247191}
```

F1 низкий: базовая модель плохо находит ушедших клиентов. Accuracy нужно
рассматривать вместе с F1, поскольку большинство клиентов относятся к классу 0.

Эндпоинт читает локальный CSV при каждом обучении. Отсутствующий файл возвращает
`404`, пустой датасет или невозможность разбиения — `422`.
Обученный Pipeline вместе с метаданными хранится в `app.state.model_bundle`
и сохраняется на диск (день 6). `POST /predict` использует его для прогноза (день 7).
Обучение также можно запустить через `/docs` → `POST /model/train` → **Try it out**
→ **Execute**.

## День 6 — Сохранение и загрузка модели

`model_storage.py` содержит функции `save_churn_model(bundle)` и
`load_churn_model()`. Через joblib сохраняется объект `ChurnModelBundle`:
обученный Pipeline, время обучения `trained_at` с часовым поясом UTC и метрики
`accuracy`/`f1`. Путь `models/churn_model.joblib` определяется относительно модуля.

После успешного `POST /model/train` создаётся папка `models`, а модель сохраняется
во временный файл и атомарно заменяет предыдущую версию. Только после успешной
записи обновляется состояние приложения. При ошибке записи возвращается `500`,
предыдущая модель остаётся доступной.

При старте FastAPI через lifespan пытается загрузить сохранённую модель.
Если файла ещё нет, сервис запускается без модели. Если файл повреждён,
ошибка записывается в лог, а сервис остаётся доступным для повторного обучения.
Загружайте только свои доверенные joblib-файлы: загрузка использует pickle.

```bash
curl -X POST http://127.0.0.1:8000/model/train
curl http://127.0.0.1:8000/model/status
```

`GET /model/status` возвращает:

- `is_trained` — есть ли обученная модель в текущем процессе;
- `trained_at` — время последнего успешного обучения в UTC, ISO 8601;
- `metrics` — метрики на test;
- `load_error` — сообщение об ошибке загрузки или `null`.
- `model_type` — тип текущего классификатора (день 8);
- `hyperparameters` — фактические параметры классификатора (день 8).

До первого обучения время и метрики равны `null`, `is_trained` равен `false`.
После обучения остановите сервер через Ctrl+C, снова запустите
`uvicorn main:app --reload` и вызовите `/model/status`: время и метрики сохранятся.
Файлы `models/*.joblib` исключены из Git.

## День 7 — Предсказание churn

`inference.py` преобразует объекты `FeatureVectorChurn` в pandas DataFrame и
передаёт их целиком в обученный Pipeline. Он применяет сохранённую предобработку,
затем `predict` и `predict_proba`. Обучение при прогнозировании не выполняется.
Вероятности связываются с метками через `model.classes_`.

`POST /predict` принимает один объект или непустой список объектов.
Для объекта возвращается `PredictionResponseChurn`, для списка — список ответов
в том же порядке (даже если передан список из одного клиента).

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H 'Content-Type: application/json' \
  -d '{"monthly_fee":29.9,"usage_hours":45.5,"support_requests":2,"account_age_months":12,"failed_payments":0,"region":"europe","device_type":"mobile","payment_method":"card","autopay_enabled":1}'
```

Пример структуры ответа (значения вероятностей иллюстративные):

```json
{"churn": 0, "probabilities": {"0": 0.8, "1": 0.2}}
```

`churn` — предсказанный класс, `probabilities["0"]` — вероятность остаться,
`probabilities["1"]` — вероятность оттока. Для пакетного запроса передайте
JSON-массив клиентов вместо объекта.

Если модель не обучена или не загружена, возвращается `503` с предложением вызвать
`POST /model/train`. Пустой список и некорректные входные данные возвращают `422`.
В `/docs` для `/predict` доступны примеры одиночного и пакетного запроса и ответа.
Низкий F1 текущей базовой модели нужно учитывать при интерпретации прогнозов.

## День 8 — Конфигурация обучения и выбор модели

`TrainingConfigChurn` описывает JSON тела запроса `POST /model/train`:

- `model_type`: `logreg` (по умолчанию) или `random_forest`;
- `hyperparameters`: словарь параметров выбранного классификатора, по умолчанию `{}`.

Пример обучения LogisticRegression:

```bash
curl -X POST http://127.0.0.1:8000/model/train \
  -H 'Content-Type: application/json' \
  -d '{"model_type":"logreg","hyperparameters":{"C":0.5,"max_iter":1000}}'
```

Пример обучения RandomForestClassifier:

```bash
curl -X POST http://127.0.0.1:8000/model/train \
  -H 'Content-Type: application/json' \
  -d '{"model_type":"random_forest","hyperparameters":{"n_estimators":100,"max_depth":8,"min_samples_leaf":2}}'
```

Оба примера доступны в `/docs`. Тело можно не передавать либо передать `{}`:
будет обучена логистическая регрессия, как в предыдущие дни.
Ответ `/model/train` по-прежнему содержит `accuracy` и `f1` на тестовой выборке.

`create_classifier(config)` создаёт выбранный классификатор. Для `logreg`
заданы `max_iter=1000` и `random_state=42`, для `random_forest` —
`n_estimators=100` и `random_state=42`. Переданные гиперпараметры перекрывают
эти значения. Остальные параметры используются по умолчанию из scikit-learn.
Обе модели работают внутри того же Pipeline с заполнением пропусков,
масштабированием чисел и OneHotEncoder. Разбиение 80/20 остаётся прежним.

Неизвестный тип модели, неизвестные параметры и некорректные значения
(например, `n_estimators=0`) возвращают `422`. Существующая модель заменяется
только после успешного обучения и сохранения новой версии.

В `ChurnModelBundle` вместе с Pipeline сохраняются `model_type` и
`hyperparameters` — фактические параметры из `classifier.get_params()`:
переданные настройки и значения по умолчанию. `GET /model/status` показывает
их вместе с временем обучения и метриками. До обучения оба поля равны `null`.
При загрузке старых файлов модели тип и параметры восстанавливаются из
сохранённого классификатора, поэтому повторное обучение для совместимости
не требуется. `/predict` использует выбранную модель без изменения формата API.

## День 9 — Единая схема признаков и предобработка

В `preprocessing.py` определён канонический порядок `FEATURE_COLUMNS`:
сначала шесть числовых признаков, затем три категориальных.
Общая функция `build_feature_frame(rows)` используется при обучении и
предсказании: проверяет наличие столбцов, выбирает только входные признаки,
упорядочивает их и приводит значения к одинаковому представлению.
Таргет `churn` не включается в матрицу признаков.

`build_preprocessor()` создаёт единый `ColumnTransformer` с двумя Pipeline:

- числовые: `SimpleImputer(strategy="median")` → `StandardScaler`;
- категориальные: заполнение `unknown` → `OneHotEncoder(handle_unknown="ignore")`.

Он включён в обучающий Pipeline вместе с выбранным классификатором.
Все обученные преобразования, категории кодировщика и классификатор
сохраняются в одном joblib-файле вместе с метаданными.
При предсказании обработчики применяются без повторного обучения.
Функция `prepare_data` дня 4 по-прежнему возвращает таблицы после заполнения
пропусков для просмотра разбиения; полный обучающий обработчик создаётся
через `build_preprocessor`.

```bash
curl http://127.0.0.1:8000/model/schema
```

`GET /model/schema` работает даже без обученной модели. Он возвращает:

- `feature_order` — внутренний порядок входных столбцов;
- `numeric_features` и `categorical_features` — явные группы признаков;
- `features` — список объектов с `name`, `type` (`float`, `int`, `str`),
  `required` и `group` для каждого признака.

Порядок ключей в JSON запроса `/predict` может быть любым: сервис сам
упорядочивает столбцы. Все девять признаков обязательны, лишние поля
(включая `churn`), пропущенные поля и бесконечные/NaN числа отклоняются с `422`.
Неизвестные текстовые категории допускаются и обрабатываются кодировщиком.
Схема описывает исходные признаки клиента, а не расширенные one-hot столбцы.

## День 10 — Единый формат ошибок

Модуль `errors.py` регистрирует глобальные обработчики `ServiceError`,
HTTP-ошибок, `RequestValidationError`, ошибок обработки данных и непредвиденных
исключений. Все HTTP-ответы с ошибками имеют одну структуру `ErrorResponse`:

```json
{
  "code": "MODEL_NOT_READY",
  "message": "Модель не обучена или не загружена. Выполните POST /model/train",
  "details": null
}
```

`code` — стабильный машинный код, `message` — описание для пользователя,
`details` — дополнительные сведения либо `null`. Стандартного внешнего поля
`detail` больше нет. HTTP-статус сохраняет своё значение независимо от `code`.

Основные ошибки:

| HTTP | code | Причина |
|---|---|---|
| 422 | VALIDATION_ERROR | Неверные типы, недостающие/лишние поля, неверный JSON |
| 422 | EMPTY_CLIENT_LIST | В `/predict` передан пустой список |
| 422 | EMPTY_DATASET | Пустой датасет при обучении или разбиении |
| 422 | INVALID_DATASET | Некорректные строки или структура CSV |
| 422 | DATA_PREPARATION_ERROR | Невозможно разделить данные на train/test |
| 422 | TRAINING_ERROR | Неподходящие гиперпараметры или данные для обучения |
| 422 | PREDICTION_ERROR | Модель не может обработать переданные признаки |
| 404 | DATASET_NOT_FOUND | Файл датасета отсутствует |
| 503 | MODEL_NOT_READY | Модель не обучена или не загружена |
| 500 | DATASET_READ_ERROR | Ошибка чтения файла |
| 500 | MODEL_SAVE_ERROR | Не удалось сохранить новую модель |
| 500 | INTERNAL_ERROR | Непредвиденный внутренний сбой |

Пример запроса с недостающими признаками:

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H 'Content-Type: application/json' -d '{"monthly_fee":"wrong"}'
```

Ответ `422` содержит `code="VALIDATION_ERROR"` и список ошибок в `details`:
для каждой ошибки указаны `location` (место в запросе), `type` и `message`.
Так как `/predict` принимает и объект, и список, валидация может описывать
ошибки обеих веток входной схемы. Исходные значения и технический контекст
исключений не включаются в ответ.

Пример некорректной конфигурации обучения:

```bash
curl -X POST http://127.0.0.1:8000/model/train \
  -H 'Content-Type: application/json' \
  -d '{"model_type":"random_forest","hyperparameters":{"n_estimators":0}}'
```

При доступном датасете ответ будет:

```json

  "code": "TRAINING_ERROR",
```
